Description

CI/CD et TDD

L'intégration et le déploiement continus (CI/CD) automatisent la validation, le build et la distribution d'un projet après chaque modification.

L'objectif est de réduire le travail manuel, de détecter les problèmes plus tôt et de garantir que chaque version du projet est construite dans un environnement reproductible.

Le développement piloté par les tests (TDD) est une méthode de développement dans laquelle les tests sont écrits avant d'implémenter la fonctionnalité elle-même.

Le travail suit un cycle d'itérations courtes : écrire un test qui échoue → implémenter le code nécessaire → refactoriser en gardant les tests au vert.

Contenu


L'intégration avec Unity passe par des workflows GitHub Actions.
Le pipeline est directement intégré à GitHub : le gestionnaire de versions devient ainsi le point d'entrée de l'automatisation.
Chaque push déclenche GitHub Actions, qui exécute le pipeline CI dans un environnement isolé et lance automatiquement le build.

Le pipeline commence par installer la version requise de l'éditeur Unity en mode batch, pour éviter d'ouvrir l'éditeur. La version de l'éditeur et les dépendances sont entièrement définies sous forme de code dans des fichiers de workflow stockés avec le projet. Chaque build s'exécute ainsi avec une configuration identique, quelle que soit la machine qui l'exécute.

Le pipeline tente ensuite de builder le projet. En cas d'échec du build ou d'un test, l'exécution est immédiatement interrompue. Le code des branches protégées par le pipeline fonctionne donc toujours (il produit un build jouable) et respecte les règles définies au départ (par les tests). Aucun push ne peut ainsi casser une autre fonctionnalité par accident, sans avoir à tout retester à la main.
Même si la mise en place peut sembler fastidieuse au début, elle finit par réduire fortement la charge de travail manuelle et améliore la fiabilité du produit : l'effort en vaut largement la peine.


Voici comment c'est mis en place.

Unity nécessite une licence : il faut donc fournir quelques informations pour que GitHub puisse utiliser la vôtre. Cela se fait via les secrets GitHub (configurables dans l'onglet Settings du dépôt). Les secrets à renseigner sont :
- UNITY_EMAIL (l'email de votre compte Unity)
- UNITY_PASSWORD (le mot de passe de votre compte Unity)
- UNITY_LICENSE (le contenu de votre licence)

L'étape suivante consiste à configurer le projet Unity.

Le jeu se trouve dans un dossier Game avec sa propre Assembly Definition, et les tests dans un dossier Tests avec une autre Assembly Definition. Le dossier Tests garantit que le système de build de Unity ne l'inclut pas dans les builds, et les Assembly Definitions permettent de le garder dans un projet séparé (.csproj) compilé indépendamment.

Comme le veut le TDD, on commence par écrire les tests. 


using NUnit.Framework; // framework used for testing


[TestFixture]
public class PlayerTests
{
    private Player player;

    [SetUp]
    public void SetUp()
    {
        player = new Player();
    }

    [Test]
    public void TakeDamage_Normal_ReducesHealth()
    {
        int damage = 20;
        player.TakeDamage(damage);

        Assert.AreEqual(player.BaseHealth - damage, player.Health);
    }

    ...
}

Explication du code

[TestFixture] -> attribut qui marque la classe pour que le pipeline la prenne en compte [SetUp] -> attribut qui désigne la méthode chargée d'initialiser la classe avant chaque test [Test] -> attribut qui marque la méthode comme méthode de test Assert -> classe statique qui détermine si le test a réussi ou échoué. Si l'assertion est fausse, le test échoue

La méthode SetUp() garantit que chaque test s'exécute sur une instance vierge de la classe.
La méthode TakeDamage_Normal_ReducesHealth() vérifie que le joueur subit bien des dégâts quand on appelle TakeDamage. La convention de nommage est MéthodeTestée_Scénario_RésultatAttendu.
On évite volontairement les valeurs codées en dur (« magiques ») : elles sont sources d'erreurs et reposent souvent sur des hypothèses (exemple ci-dessous). 


// same method but poorly implemented
[Test]
public void TakeDamage_Normal_ReducesHealth()
{
    player.TakeDamage(20); // we decide to apply 20 damage

    Assert.AreEqual(80, player.Health);
    // the 80 value seems to come out of nowhere (mostly cause it kinda does)
    // here 80 is based on several assumptions:
    // 1 -> assumes base health is 100 (will break the test if the base health ever change)
    // 2 -> assumes correct maths and no typos
    // (any maths failure or typo would result in an incorrect result)
}

On peut maintenant écrire le code qui satisfait le test. 


public sealed class Player
{
    public const int BaseHealth = 100;
    public int Health { get; private set; } = BaseHealth;

    public void TakeDamage(int amount)
    {
        Health = Mathf.Max(0, Health - amount);
    }

    ...
}

Cette implémentation minimale passe le test, mais ce seul test ne suffit pas : il reste des failles. Par exemple, infliger des dégâts négatifs soignerait le joueur. Si c'est le comportement voulu, tant mieux, mais il faut quand même le tester. C'est pourquoi on développe toute une série de tests pour couvrir les cas limites. 


// PlayerTests.cs
[Test]
public void TakeDamage_WithNegativeAmount_DoesNotChangeHealth()
{
    player.TakeDamage(-10);

    Assert.AreEqual(player.BaseHealth, player.Health);
}
// this simple test highlights that issue and forces us to adapt the code

// Player.cs
public void TakeDamage(int amount)
{
    if (amount <=  0)
        return;

    Health = Mathf.Max(0, Health - amount);
}

Toute modification future de la méthode devra toujours respecter les tests, ce qui évite de casser son comportement.

Voici à quoi ressemble un push réussi.

Voilà tout l'intérêt du TDD et de la CI/CD. On écrit les tests en fonction du comportement attendu.
On écrit ensuite le code qui respecte ces tests, et donc le comportement attendu.
Enfin, le pipeline CI/CD exécute les tests et empêche votre code d'être cassé.
