Description

A small 2D game engine to learn C++

I built this engine to learn C++. Coming from Unity and C#, I wanted to understand what an engine does under the hood, so I rebuilt the parts I used every day on top of SFML: a main loop, scenes, GameObjects and components, coroutines, events and resource caching.

Its API deliberately mirrors Unity's (Awake, GetComponent, StartCoroutine, WaitForSeconds...) so I could focus on how to implement those features in C++ rather than on designing a new API. Along the way it became my playground for the language: templates, smart pointers, lambdas, RTTI and operator overloading.

Content

Main loop and modules

The Engine owns a list of modules: the window, time, inputs and the scene manager. Each one derives from Module, which exposes virtual Init, Update, Render, PostRender and Shutdown methods, and the main loop simply calls each step on every module, in order, until the window is closed.

Adding a system to the engine is just a new Module subclass and one line in CreateModules(). The order of that list is the order the modules run in, every frame. 


void Engine::Run()
{
    CreateModules();

    Init();

    while (ShouldRun())
    {
        Update();
        Render();
        PostRender();
    }

    Shutdown();
}

void Engine::CreateModules() {
    CreateModule<Window>();
    CreateModule<TimeModule>();
    CreateModule<InputsManager>();
    CreateModule<SceneManager>();
}

void Engine::Update()
{
    for (Module* module : Instance->modules)
    {
        module->Update();
    }
}

// Engine.hpp
template<typename ModuleType> inline void CreateModule()
{
    modules.push_back(new ModuleType());
}

GameObjects and components

Scenes own GameObjects, and GameObjects own their components through std::shared_ptr. AddComponent<T>() creates the component, gives it its owner and queues its Awake() on the scene, so it runs at the start of the next update, once the GameObject has been fully set up. 


template<typename TComponent> inline std::shared_ptr<TComponent> GameObject::AddComponent()
{
    std::shared_ptr<TComponent> componentPtr = std::make_shared<TComponent>();
    std::shared_ptr<Component> asComponent = std::static_pointer_cast<Component>(componentPtr);

    asComponent->SetOwner(this);

    components.push_back(asComponent);

    ParentScene->QueueAwake([=]() { asComponent->Awake(); });

    return componentPtr;
}

template<typename TComponent> inline std::shared_ptr<TComponent> GameObject::GetComponent(int skipOccurences)
{
    for (std::shared_ptr<Component> component : components)
    {
        std::shared_ptr<TComponent> relevantComponent = std::dynamic_pointer_cast<TComponent>(component);

        if (relevantComponent == nullptr) { continue; }

        if (skipOccurences-- > 0) { continue; }

        return relevantComponent;
    }

    return nullptr;
}

I tried two ways of storing components, switchable with a #define:
- a map from typeid(T).name() to a list of components: a direct lookup, but GetComponent<Renderable>() can't find a Sprite, because the key is the exact type;
- a single vector scanned with std::dynamic_pointer_cast: a linear scan and an RTTI cast per component, but lookups by base class work.

The engine uses the second one, since Sprite, Circle and Rectangle all derive from Renderable. A GameObject only holds a handful of components, so the scan stays cheap and the flexibility is worth it.

Coroutines

Unity's coroutines are built on C# iterators (yield return). C++20 coroutines exist, but they need a lot of plumbing (promise types, awaiters...), so I built a simpler system closer to Unity's model: a coroutine is a list of steps, either segments (lambdas that run in one go) or yield instructions that decide whether to continue, wait, or exit. A loop is a yield instruction that jumps back to a saved position. 


// usage: print, wait 2.5 seconds, print again, loop forever
coroutine.AddSegment(
    [&]() {
        std::cout << "Hi" << std::endl;
    }
);
coroutinesLoopAnchors.push_back(new Coroutine::ProgressData());
coroutine.AddControlFlow(
    new Coroutine::YieldInstructions::WaitForSeconds(2.5f), coroutinesLoopAnchors[0]
);

coroutine.AddSegment(
    [&]() {
        std::cout << "Hi again" << std::endl;
    }
);

coroutine.AddControlFlow(
    new Coroutine::YieldInstructions::DoWhileLoop(coroutinesLoopAnchors[0], [] { return true; })
);

StartCoroutine(coroutine);

// Coroutine::Update(), called every frame: returns whether the coroutine is over
while (progressData.Step < totalSteps)
{
    if (isControlFlow[progressData.Step])
    {
        int ctrlFlowIndex = progressData.ControlFlowIndex; // can change within evaluate
        switch (controlFlow[ctrlFlowIndex]->Evaluate(&progressData))
        {
            case YieldInstructions::Result::Proceed:
                controlFlow[ctrlFlowIndex]->Reset();
                progressData.ControlFlowIndex++;
                break;

            case YieldInstructions::Result::Wait:
                return false;

            case YieldInstructions::Result::Exit:
                progressData.Step = 0;
                started = false;
                return true;
            ...
        }
    }
    else
    {
        segments[progressData.SegmentIndex++]();
    }

    progressData.Step++;
}

Templates everywhere

This project is where I got comfortable with templates. The scene manager loads any number of scenes with a fold expression, and the resource manager loads each texture, sound or font once, then hands out the cached copy, keyed by type and path. 


template <typename ...ScenesNames> static void LoadScenes(bool additive = false)
{
    if (!additive)
    {
        UnloadAllScenes();
    }

    (LoadScene<ScenesNames>(true), ...);
}

template <typename ResourceType> std::shared_ptr<ResourceType> ResourceManager::Load(const std::string& path)
{
    const std::string& resourceTypeAsStr = NameOfType<ResourceType>();

    if (resources[resourceTypeAsStr].contains(path))
    {
        return std::static_pointer_cast<ResourceType>(resources[resourceTypeAsStr][path]);
    }

    std::shared_ptr<ResourceType> newResource = std::make_shared<ResourceType>();
    std::static_pointer_cast<ResourceTypes::Resource>(newResource)->Load(path);

    resources[resourceTypeAsStr][path] = newResource;

    return newResource;
}

What it taught me

Beyond the syntax, this engine taught me to think about ownership and lifetimes, which C# had always handled for me: who owns an object, when it gets destroyed, and what a lambda capture keeps alive. It also taught me how templates are compiled, why their definitions have to live in headers (the .inl files), and what RTTI and dynamic casts cost.

Looking back, I would let std::unique_ptr own the modules and GameObjects instead of raw new and delete, and keep std::shared_ptr for the few objects that are really shared.
