Description

Un petit moteur de jeu 2D pour apprendre le C++

J'ai créé ce moteur pour apprendre le C++. Venant de Unity et du C#, je voulais comprendre ce qu'un moteur fait en coulisses, alors j'ai recréé par-dessus SFML les éléments que j'utilisais tous les jours : une boucle principale, des scènes, des GameObjects et des composants, des coroutines, des événements et un cache de ressources.

Son API reprend volontairement celle de Unity (Awake, GetComponent, StartCoroutine, WaitForSeconds...) pour que je puisse me concentrer sur la façon d'implémenter ces fonctionnalités en C++ plutôt que sur la conception d'une nouvelle API. Il est aussi devenu mon terrain d'expérimentation pour le langage : templates, smart pointers, lambdas, RTTI et surcharge d'opérateurs.

Contenu

Boucle principale et modules

L'Engine possède une liste de modules : la fenêtre, le temps, les entrées et le gestionnaire de scènes. Chacun hérite de Module, qui expose les méthodes virtuelles Init, Update, Render, PostRender et Shutdown, et la boucle principale appelle simplement chaque étape sur chaque module, dans l'ordre, jusqu'à la fermeture de la fenêtre.

Ajouter un système au moteur revient à créer une sous-classe de Module et à ajouter une ligne dans CreateModules(). L'ordre de cette liste est l'ordre dans lequel les modules s'exécutent, à chaque frame. 


void Engine::Run()
{
    CreateModules();

    Init();

    while (ShouldRun())
    {
        Update();
        Render();
        PostRender();
    }

    Shutdown();
}

void Engine::CreateModules() {
    CreateModule<Window>();
    CreateModule<TimeModule>();
    CreateModule<InputsManager>();
    CreateModule<SceneManager>();
}

void Engine::Update()
{
    for (Module* module : Instance->modules)
    {
        module->Update();
    }
}

// Engine.hpp
template<typename ModuleType> inline void CreateModule()
{
    modules.push_back(new ModuleType());
}

GameObjects et composants

Les scènes possèdent les GameObjects, qui possèdent leurs composants via des std::shared_ptr. AddComponent<T>() crée le composant, lui assigne son propriétaire et met son Awake() en file d'attente sur la scène : il s'exécute ainsi au début de l'update suivant, une fois le GameObject entièrement configuré. 


template<typename TComponent> inline std::shared_ptr<TComponent> GameObject::AddComponent()
{
    std::shared_ptr<TComponent> componentPtr = std::make_shared<TComponent>();
    std::shared_ptr<Component> asComponent = std::static_pointer_cast<Component>(componentPtr);

    asComponent->SetOwner(this);

    components.push_back(asComponent);

    ParentScene->QueueAwake([=]() { asComponent->Awake(); });

    return componentPtr;
}

template<typename TComponent> inline std::shared_ptr<TComponent> GameObject::GetComponent(int skipOccurences)
{
    for (std::shared_ptr<Component> component : components)
    {
        std::shared_ptr<TComponent> relevantComponent = std::dynamic_pointer_cast<TComponent>(component);

        if (relevantComponent == nullptr) { continue; }

        if (skipOccurences-- > 0) { continue; }

        return relevantComponent;
    }

    return nullptr;
}

J'ai essayé deux façons de stocker les composants, interchangeables via un #define :
- une map de typeid(T).name() vers une liste de composants : un accès direct, mais GetComponent<Renderable>() ne trouve pas un Sprite, car la clé est le type exact ;
- un seul vecteur parcouru avec std::dynamic_pointer_cast : un parcours linéaire et un cast RTTI par composant, mais la recherche par classe de base fonctionne.

Le moteur utilise la seconde, puisque Sprite, Circle et Rectangle héritent tous de Renderable. Un GameObject ne contient qu'une poignée de composants : le parcours reste peu coûteux et la flexibilité en vaut la peine.

Coroutines

Les coroutines de Unity reposent sur les itérateurs C# (yield return). Les coroutines C++20 existent, mais demandent beaucoup de mise en place (promise types, awaiters...), alors j'ai construit un système plus simple, proche du modèle de Unity : une coroutine est une liste d'étapes, soit des segments (des lambdas exécutées d'un bloc), soit des instructions de yield qui décident s'il faut continuer, attendre ou sortir. Une boucle est une instruction de yield qui revient à une position sauvegardée. 


// usage: print, wait 2.5 seconds, print again, loop forever
coroutine.AddSegment(
    [&]() {
        std::cout << "Hi" << std::endl;
    }
);
coroutinesLoopAnchors.push_back(new Coroutine::ProgressData());
coroutine.AddControlFlow(
    new Coroutine::YieldInstructions::WaitForSeconds(2.5f), coroutinesLoopAnchors[0]
);

coroutine.AddSegment(
    [&]() {
        std::cout << "Hi again" << std::endl;
    }
);

coroutine.AddControlFlow(
    new Coroutine::YieldInstructions::DoWhileLoop(coroutinesLoopAnchors[0], [] { return true; })
);

StartCoroutine(coroutine);

// Coroutine::Update(), called every frame: returns whether the coroutine is over
while (progressData.Step < totalSteps)
{
    if (isControlFlow[progressData.Step])
    {
        int ctrlFlowIndex = progressData.ControlFlowIndex; // can change within evaluate
        switch (controlFlow[ctrlFlowIndex]->Evaluate(&progressData))
        {
            case YieldInstructions::Result::Proceed:
                controlFlow[ctrlFlowIndex]->Reset();
                progressData.ControlFlowIndex++;
                break;

            case YieldInstructions::Result::Wait:
                return false;

            case YieldInstructions::Result::Exit:
                progressData.Step = 0;
                started = false;
                return true;
            ...
        }
    }
    else
    {
        segments[progressData.SegmentIndex++]();
    }

    progressData.Step++;
}

Des templates partout

C'est avec ce projet que je suis devenu à l'aise avec les templates. Le gestionnaire de scènes charge un nombre quelconque de scènes avec une fold expression, et le gestionnaire de ressources charge chaque texture, son ou police une seule fois, puis renvoie la copie en cache, indexée par type et par chemin. 


template <typename ...ScenesNames> static void LoadScenes(bool additive = false)
{
    if (!additive)
    {
        UnloadAllScenes();
    }

    (LoadScene<ScenesNames>(true), ...);
}

template <typename ResourceType> std::shared_ptr<ResourceType> ResourceManager::Load(const std::string& path)
{
    const std::string& resourceTypeAsStr = NameOfType<ResourceType>();

    if (resources[resourceTypeAsStr].contains(path))
    {
        return std::static_pointer_cast<ResourceType>(resources[resourceTypeAsStr][path]);
    }

    std::shared_ptr<ResourceType> newResource = std::make_shared<ResourceType>();
    std::static_pointer_cast<ResourceTypes::Resource>(newResource)->Load(path);

    resources[resourceTypeAsStr][path] = newResource;

    return newResource;
}

Ce que ce projet m'a appris

Au-delà de la syntaxe, ce moteur m'a appris à réfléchir à la possession et à la durée de vie des objets, que le C# gérait toujours pour moi : qui possède un objet, quand il est détruit, et ce qu'une capture de lambda garde en vie. Il m'a aussi appris comment les templates sont compilés, pourquoi leurs définitions doivent se trouver dans les headers (les fichiers .inl), et ce que coûtent le RTTI et les dynamic casts.

Avec le recul, je confierais la possession des modules et des GameObjects à des std::unique_ptr plutôt qu'à des new et delete bruts, et je garderais les std::shared_ptr pour les quelques objets réellement partagés.
